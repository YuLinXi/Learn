# M09 · 两个公司项目的核心架构

前置：M06 可开始职责与产物阅读；完整验收依赖 M07/M08。目标是解释可见架构、关键分支与修改影响，不以复刻引擎为目标。

## 阅读范围

以 [源码地图](../../PROJECT-STACK.md) M09 表为定位入口。UDC 实体相关阅读先进入其 CONTEXT-MAP 对应实体域文档，使用标准实体、单据实体等真实领域术语；不要把全部设计对象都当成数据库表。

## A · UDC：设计、生成、发布与运行边界

1. 选一种已有实体设计，定位设计元数据与 schema；从 AutoCodeExecutor 跟到 EntityTask，解释生成任务、产物与元数据写出。
2. 任选一种发布方式，从 DeploymentService 到 PipeLineManager，解释请求返回、任务执行、状态读取。Future 类型本身不证明是否异步，要看调用方式。
3. 在同一张图补字典删除的发送者与监听器及子项处理；EventBus 内部不可见时保留同步性、异常传播和回滚保证待验证。
4. 定位运行侧 starter 的依赖或消费契约；本轮止于可见调用侧及运行边界。以后追踪生成应用真实运行请求时再补 udc-starters 和环境证据。

## B · CDP：定义、执行、查询与结果

1. 在 M06 基础图上补明细/统计分支，说明 Gateway、查询引擎、JDBC 会话、结果适配各承担什么。
2. 用一张小表对照：未保存设计预览、已保存后台预览、前台运行。列输入来源、权限检查、是否进入引擎、内容状态/结果，分别标明元数据访问与目标业务查询。
3. 结合固定销售口径，选公司汇总或分页测试解释期望；识别公司引擎还负责规划、权限、资源和结果结构，不能用小练习替代这些验证。
4. 读 IntegrationAdapterResolver 的零/唯一/多个候选分支，解释插件是否启用和是否实例化；选择一个实际边界，不通读全部集成。
5. 解释一个并发限制/资源释放位置；数据库与内存策略达到职责识读层，复杂算法按工作需要深入。

## 本轮验收

- [ ] 两张可增补链路图，关键节点有文件、符号、test 提交和职责说明。
- [ ] UDC 设计→生成→发布及运行侧边界可说明，事件/异步行为不超出可见证据。
- [ ] CDP 三场景权限与明细/统计路径能对照，区分短路和结构化空结果。
- [ ] 针对一个未提前给答案的小需求，指出修改点、契约、权限/事务、失败路径与回归范围。
- [ ] 能清楚区分源码确认、调用契约推断、不可见实现和运行待验。

图和影响分析可以写在一份 [练习报告](../../templates/exercise-report.md) 中；不新增多套架构报告。公司测试未执行就标已读/解释预期，公司运行维度独立保存。

## 完成之后

根据实际公司任务补缺失实现或深入一个机制；保留本轮已验证能力，只补未知环节。真实需求中的代码改动和部署另按仓库工作流程执行。
