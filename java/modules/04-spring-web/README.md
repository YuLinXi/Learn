# M04 · Spring Web 与框架机制

前置：M02、M03。目标是独立完成一个内存接口，再解释框架为它做了什么。

## 定向阅读

[R01/R02/R05](../../RESOURCES.md)：22.1 IoC、22.4.1–22.4.4 Web、23.1/23.5/23.7；先按 REST Guide 理解输入输出。遇到机制问题再读 22.2、5.1/5.3/5.6、第 6 章；JSON 契约补 17.4。

先看 [版本差异卡](../../RESOURCES.md#练习与公司版本差异卡)，使用本地 Web 骨架的 POM。Bean、注解、反射和代理达到能解释当前路径的深度。

## 小任务顺序

1. 创建 [字典契约](../../practice/DICTIONARY.md) D1 的一个 POST 接口，手工发真实 HTTP 请求，核对状态码与 JSON。
2. 分出 DTO、Controller 与构造注入的 Service，再完成读取、更新、删除、分页；存储保持内存。
3. 加入校验和统一错误响应；验证正常、非法输入、不存在及重复业务键，不把所有失败都返回 200。
4. 选两项 JSON 契约验证：大整数 ID 的字符串表达，以及缺失/null 的区别。记录请求、响应和前端消费含义，金额/时区按实际需要再加入。
5. 解释扫描、Bean 创建、注入、方法调用；对照公司一个可见装配点和 UDC Controller。识别普通 new 对象与容器对象，区分注解元数据与读取它的机制。
6. 用一题代理调用解释为 M05 事务铺垫；不要求自己实现容器或代理框架。

## 本轮验收

- [ ] 核心业务逻辑本人实现，可查文档；成功和契约失败均有真实 HTTP 或对应层测试证据。
- [ ] 能从 JSON 输入解释到 DTO、Service 和返回值，说明参数校验如何接入。
- [ ] 两项 JSON 边界按契约验证，能解释 Java 与 TypeScript 看到的值。
- [ ] 解释一个 Bean 的创建、依赖和配置来源；对照公司注解时明确未知注册机制。
- [ ] 独立完成一次小契约变化并补验证。

MockMvc 能验证 Web 层行为，但不代替真实网络与数据库验证。公司序列化规则独立核实，不直接套用本练习。
